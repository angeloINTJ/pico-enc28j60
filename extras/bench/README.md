# On-hardware bench test

Checks that the library really works with an ENC28J60 on a real LAN, using
traffic generated by your PC:

| Test      | What it proves                                                              |
|-----------|-----------------------------------------------------------------------------|
| `init`    | the chip answers over the PIO SPI (revision ID) and the link comes up       |
| `errpath` | `begin()` fails fast (no hang) when no chip answers, and can be retried     |
| `ping`    | ARP + ICMP echo: unicast RX and TX, host ARP cache learns the board's MAC   |
| `rx`      | 200 broadcast UDP frames of mixed sizes arrive in order, intact, no repeats |
| `echo`    | 200 unicast UDP round trips PC -> board -> PC, payload compared byte by byte |
| `soak`    | 5000 frames of mixed sizes: none repeated, reordered, lost or corrupted      |
| `rxflood` | a flood of full-size frames back to back: what arrives is intact and the receiver is in step afterwards (at the default clock the buffer of the chip overflows, at 20 MHz it keeps up and the switch drops the rest) |
| `rxoverflow` | the receive buffer overflows on purpose, at any clock: the oldest frames stay, `hasRXError()` reports it, the acknowledge clears it, and a clean stream follows |
| `discard` | frames wait in the buffer while the board does not serve the chip: `hasPacket()`, `available()` and `peekInterruptFlags()` say so, `discardFrame()` drops one unseen without disturbing the next |
| `callback` | the interrupt callback of `setInterruptCallback()`: called by the handler of the INT pin, or by `poll()` without it, once per event |
| `linkflag` | the PHY is powered down and up: `hasLinkChange()` reports each change, with or without the INT pin, and `acknowledgeInterrupts()` clears it |
| `setmac` | `setMACAddress()` while the chip works: the registers hold the new address, the board answers for it, it survives a reset of the chip, and the old one comes back |
| `spi` | 2000 rounds of random data through every kind of access (an ETH register, the MAC registers, the PHY, the buffer memory) at 1, 3.5, 8 and 10 MHz must come back intact, and the clocks up to 20 MHz are reported with the time of a frame |
| `tx`, `txlong`, `txburst`   | board streams unicast frames to the PC (100, 400, and 200 back to back) |
| `txb`, `txblong`, `txbburst`| same, as broadcast (does not depend on the board's RX path)            |
| `cfgerr`  | seven kinds of configuration that make no sense are refused at once, each as a `config` error, without touching a pin |
| `pioful`  | with no room in any PIO, `begin()` fails with `piospace` and quickly, and the real `begin()` afterwards works |
| `txstat`  | the transmit status vector of frames of several sizes, unicast and broadcast: bytes on the wire, flags, no collisions |
| `pioshare`| other users of the PIO (`SerialPIO`) take every other state machine; the one of the driver stays its own and works |
| `stall`   | the state machine is stopped: the call that finds out returns in a few milliseconds, and the driver brings the chip back |
| `lifecycle` | `end()` then `begin()`, several times: the state machine is given back each time and the chip works after the last |
| `txmix`   | with the longest receive buffer, which leaves room for one frame to send from, frames of all lengths still go out |
| `txring`  | frames go out the way the lwIP interface sends them, the next one uploaded while the one before is on the wire: with the default receive buffer no upload waits for the wire, with longer ones frames of mixed lengths find room after the pointers wrapped, none dropped, no frame is given bytes of the one on the wire (seven frames with a receive buffer of `0x145A` used to do that), every one intact |
| `lostchip`| the chip is reset behind the back of the driver, as a glitch of its supply would: `checkChip()` notices, configures it again, and ping works |
| `txfull`  | 200 broadcast frames with a 1472-byte payload, back to back: all of them arrive intact, and the time of the whole stream (`us=` in the `TXDONE` line) gives the frames and the kB a second that `sendFrame()` reaches at the SPI clock of the build; reported, not judged |
| `cost`    | the commands of the SPI that `available()` on an empty buffer, `receiveFrame()` of a frame, an upload and the start of a transmission take, counted by the driver itself (below), only with `--profile`: none may take more than the code needs, which is 3, 11 + ceil(S/31) with S the bytes that `receiveFrame()` returns, 5 + ceil(L/30) for an upload of L bytes, and 10 (the arithmetic is in `cost_budget()` in `bench.py`). The microseconds of each step, and of the wait for the end of the frame, are reported |

`cost` needs `-DENC28J60_PROFILE`: the C driver then counts the commands that `enc28j60_execute_blocking()` runs and the microseconds they take, and the wait for the end of a transmission counts its reads of `EIR` and its microseconds (`src/enc28j60-cmd.h`); without the define none of that is compiled, and that is the build that users get. So `cost` runs only with `--profile`, the way the interrupt tests run only with `--irq`: `--flash --profile` builds `BenchTest` with the define in both `compiler.c.extra_flags` and `compiler.cpp.extra_flags` and adds `cost` to the default tests, while `--flash` alone builds it without, as before. The gate runs `cost` in a suite of its own, `bench_cost`, and everything else on the build without the define; the CI builds do not use the define either. A board built without it answers `COSTERR noprofile`, and `--tests cost` without `--profile` stops at once. `txfull` works in both builds.

With `--irq GPIO` (the chip's INT wired to that pin) the board is built so that its
main loop touches the chip only when the INT line asks it to. Everything above then
runs on top of the interrupt, and three more tests check the interrupt itself:

| Test      | What it proves                                                              |
|-----------|-----------------------------------------------------------------------------|
| `irqidle` | 8 quiet seconds: every edge on INT belongs to a frame, none are spurious, and the line is high afterwards |
| `irqedge` | 100 frames 50 ms apart: each one raises the line and is received            |
| `irqlink` | the PHY is powered down and up: the interrupt reports both link changes, and traffic works afterwards |

`rx` also reports whether `receiveFrame()` includes the 4-byte Ethernet FCS.

## The asynchronous functions of the C driver

The C driver has two sets of functions: the blocking ones (`*_blk`), which the Arduino classes use, and the
asynchronous ones, which build a list of commands, send it through DMA and wait for an interrupt. Only the
FreeRTOS+TCP driver in `freertos/` uses the asynchronous ones, and that driver is not built here. `BenchTest` can serve
the chip with them in place of the Arduino class: the serial command `ASYNC 1` hands the chip over, `ASYNC 0` gives it
back, and in between `loop()` does what the interrupt branch of the task of the FreeRTOS driver does, call for call
(`AOPT` sets whether the read pointer of the chip is checked after every frame and whether frames are dropped unseen).
`bench.py` switches the mode by itself: once for the first six tests below, which run one after the other, and
`asynccycle` runs last of all and does its own starting and stopping.

| Test      | What it proves                                                              |
|-----------|-----------------------------------------------------------------------------|
| `asyncrx` | 200 frames of mixed sizes through `enc28j60_frame_rx()`, with `ERXRDPT` read back from the chip after every frame: it is odd each time (silicon errata, issue 14), and every frame arrives intact and in order |
| `asyncdiscard` | `enc28j60_frame_discard()` on every frame: none is delivered, `ERXRDPT` is odd after each, and a clean stream follows |
| `asyncfast` | 3000 small frames 1 ms apart, with no delay and no other SPI between one asynchronous call and the next, as in the FreeRTOS driver: all arrive intact and in order, no frame header is bad, no wait for the DMA times out, and nothing is left in the buffer |
| `asyncecho` | 200 unicast UDP round trips, each reply sent right after the frame was read |
| `asynctx` | 200 broadcast frames sent with `enc28j60_frame_upload()` and `enc28j60_frame_tx()`, one waiting and one on the wire, the transmit interrupt moving the next one to the transmitter: all of them arrive |
| `asyncflood` | back-to-back full-size frames overflow the receive buffer: what arrives is intact, no frame header is bad, no wait times out, and a clean stream follows |
| `asynccycle` | `enc28j60_init()` and `enc28j60_deinit()` eight times in a row, with a command through DMA each time: the same DMA channels are claimed and the same heap is free afterwards. It runs last because a driver that keeps the 3 channels it takes at each start runs out of the 12 of the RP2040 and stops the firmware; the board prints `ASYNCCYCLE_STEP n` before each start, so a run that dies shows how far it got |

The six tests that share the session also check that no wait for the DMA timed out (`waitto`) and, where the board
sends, that no frame was given up for lack of room (`txto`). In this mode the Arduino class is stopped, so the
board answers `ASYNCERR active` to the commands that go through it.

## What you need

* A Pico wired to an ENC28J60 and cabled to the same LAN as the PC. The sketch
  uses the `ENC28J60Config` default pins (SCK=GP2, MOSI=GP3, MISO=GP4, CS=GP5,
  RST=GP7); edit `makeConfig()` in `BenchTest.ino` if yours differ.
* A free IPv4 address on that LAN for the board. The sketch does not use DHCP.
* `arduino-cli` with the arduino-pico core (only for `--flash`) and
  `pip install pyserial`.

No root is needed. The TX streams are unicast to a socket the PC opened itself,
so a default-deny firewall does not get in the way.

## Run

```
python3 extras/bench/bench.py --ip 192.168.3.77 --flash
python3 extras/bench/bench.py --ip 192.168.3.77 --flash --irq 6   # INT wired to GP6
```

`--flash` compiles `BenchTest` against **this checkout** (not the copy in your
Arduino libraries folder) and uploads it. Select tests with
`--tests init,ping,rx`. The exit code is 0 only if everything passed.

 * `--spi-hz N` builds the sketch with that SPI clock instead of the default of the
   library, to run every test at another clock. `--spi-assert-mhz M` is how fast the
   `spi` test needs the clocks to be clean (default 8); the faster ones are reported.
 * `--alt-ip` is the second free address that `setmac` needs (default: `--ip` plus two).
 * `--profile` builds the sketch with `-DENC28J60_PROFILE` when `--flash` is given, and adds the `cost` test to the
   default tests (see the paragraph on `cost` above).

## lwIP interface test

`BenchLwip` is the sketch for `PicoENC28J60lwIP`, driven by `benchlwip.py`, which is
the other side of the network. It needs a DHCP server on the LAN and, for the static
address test, one free address:

```
python3 extras/bench/benchlwip.py --flash --static-ip 192.168.3.78
python3 extras/bench/benchlwip.py --flash --irq 6 --static-ip 192.168.3.78   # INT wired to GP6
```

`--spi-hz N` builds the sketch with another SPI clock, as in `bench.py`.

| Test      | What it proves                                                              |
|-----------|-----------------------------------------------------------------------------|
| `dhcp`    | the interface gets an address from the DHCP server, on the network of the PC |
| `ping`    | the PC pings the board, also with 1400-byte payloads (3000-byte pings, which are fragmented, are reported) |
| `tcp`     | 200000 random bytes, in chunks of random sizes, are echoed through one connection by the TCP server of the board |
| `tcppar`  | three connections at once, each asking and getting an answer 150 times |
| `tcpbulk` | 64 kB through each of three connections at once, in chunks of random sizes, twice: they all come back intact within seconds, and none stalls |
| `rxbuf`   | 11 kB that the peer sent and the application did not read yet wait in lwIP: they leave the heap of lwIP (16 KB in the core) as it was |
| `tcpcycle`| 40 connections opened, used and closed in a row: all work, the heap does not shrink |
| `udp`     | datagrams of 1 to 1472 bytes are echoed, none lost or corrupted (a 3000-byte one, fragmented, is reported) |
| `pingout` | the board pings the PC |
| `client`  | the board opens a TCP connection to the PC and moves 100 kB each way, checked byte by byte |
| `udpsend` | the board sends 100 UDP datagrams to the PC |
| `udprate` | the board sends 500 full-size UDP datagrams to the PC with no pause, timed on the board: how fast frames go out through lwIP; every one has to arrive intact and be counted by the driver as sent, and at the default SPI clock a frame has to take less than one that is uploaded and then waited for (its time on the wire plus its bytes through the SPI: 2.43 ms at 10 MHz), which only uploading it while the one before is on the wire does |
| `chain`   | the board sends UDP datagrams as chains of three buffers, which arrive whole |
| `dns`     | the board resolves a name (reported; add `--dns-name` to make it a test) |
| `flap`    | the PHY is powered down and up, like a cable pulled out and put back: the link change is seen, lwIP is told, the DHCP client asks again, and ping and TCP work afterwards |
| `lostchip`| the chip is reset behind the back of the interface: it notices within a second, configures the chip again, and ping and TCP work |
| `static`  | a static address instead of DHCP (needs `--static-ip`), then DHCP again |
| `lifecycle` | `end()` and `begin()` three times: every start gets an address and the heap does not shrink |
| `heap`    | the free heap at the end against the beginning |

The sketch answers `DIAG`, which prints the
registers of the chip and the pointers of the driver, for finding out why a
transfer failed.

## Web server test

`examples/WebServerLedToggle` has its own test, which needs only the address the
board prints on the serial port:

```
python3 extras/bench/webtest.py --ip 192.168.3.39 --soak 300
```

Compile the example with `-DINT_PIN=6` (or edit the constant at its top) to test it
driven by the INT pin.

It checks sequential and parallel requests, that 100 toggles leave the LED and
the level read back from the pin consistent, and, with `--soak`, that the free
heap does not shrink.

## Notes

* `ping` exercises the board's ARP responder only if the PC has no cached entry
  for the board's address (the first run after the address changes). Clearing the
  cache needs root (`ip neigh flush`), so the test does not do it.

* The ENC28J60 is 10 Mbit/s half duplex and this driver talks SPI at 10 MHz unless
  you ask for another clock, so reading a full-size frame takes about 1.3 ms (the
  `spi` test prints the time at each clock). The harness paces the streams
  accordingly. `txburst`/`txbburst` send with no gap on purpose.
* With the default clock, reading frames from the chip does not keep up with a
  10 Mbit/s flood of full-size frames, and the buffer of the chip overflows; that is
  a limit of the hardware and the clock, not a test failure to chase. `rxflood`
  floods on purpose and only asks for intact frames; `rxoverflow` makes the buffer
  overflow whatever the clock, and checks what the driver does about it.

## The whole gate

`gate.sh` runs the suites above on a board, one after the other, each into its own log, and
ends with a summary that says which passed. The exit status is 0 only if every suite that ran
passed. It compiles and flashes **the checkout it is in**, so a branch or a worktree is tested
by running its own copy of the script. **A change to the driver, to the PIO program or to the
lwIP interface goes in only after the gate passed on a board.** Say in the pull request which
options you ran, and paste the summary.

```
extras/bench/gate.sh --ip 192.168.3.77 --irq 6 --web-mac c2:62:13:20:3e:27
```

| Suite | What it runs |
|-------|--------------|
| `bench_poll`, `bench_irq` | `bench.py --flash`; `bench_irq` is the interrupt build (`--irq`) |
| `bench_cost` | `bench.py --flash --profile --tests cost`, polled, right after `bench_poll`: the build with the counters of the driver (`-DENC28J60_PROFILE`), which is not the build that users get, so no other suite runs the `cost` test |
| `lwip_poll`, `lwip_irq` | `benchlwip.py --flash --static-ip`; `lwip_irq` is the interrupt build (`--irq`) |
| `web_poll`, `web_irq` | compiles `examples/WebServerLedToggle` (with `-DINT_PIN=<GPIO>` for `web_irq`), flashes it, finds the board on the LAN by its MAC address, and runs `webtest.py --soak` on it |

The `_irq` suites run with `--irq`, and the web suites with `--web-mac` and without `--spi-hz`
(the example has no such option). A suite that does not run is named in the summary, with the
reason. Without `--irq` and `--web-mac` the gate is the polled suites: `bench_poll` and
`bench_cost` of `bench.py`, and `lwip_poll` of `benchlwip.py`.

| Option | |
|--------|-|
| `--ip ADDR` | Required: a free address for `bench.py`. The address plus 2 has to be free too (the `setmac` test) |
| `--lwip-ip ADDR` | A free address for the static address test of `benchlwip.py`. Default: `--ip` plus 1 |
| `--irq GPIO` | The INT pin of the chip is wired to this GPIO. Every suite then also runs in its interrupt build |
| `--web-mac MAC` | The MAC address of the web example (below). With it the web suites run |
| `--soak SECONDS` | The length of the soak in each web suite. Default: 240 |
| `--spi-hz HZ` | The SPI clock of `bench.py` and `benchlwip.py`. `--spi-assert-mhz` is set to the same clock, so that the `spi` test asks for clean transfers at it |
| `--port PORT` | The serial port of the Pico. Default: the only `/dev/serial/by-id/*Pico*`; with more than one Pico connected the gate stops and asks for it, so that no other board gets flashed (`bench.py` and `benchlwip.py` do the same). Uploads use the device node that it points to, which is what the uploader of the core needs |
| `--out DIR` | Where the logs and the summary go. Default: `$TMPDIR/picoenc-gate`, or `/tmp/picoenc-gate` |
| `--fqbn FQBN` | The board. Default: `rp2040:rp2040:rpipico` |

It takes about 16 minutes with `--irq`, `--web-mac` and the default soak (the bench of the
author, October 2026); the two soaks are 8 of those minutes. It needs Linux (for the serial
port and `ip neigh`), `arduino-cli` with the core, pyserial and `ping`, the PC on the same /24 as
the board, and with `--web-mac` also `curl` and `ip`. No root.

`summary.txt` in the output folder is the result, and `<suite>.txt` is the log of each suite:

```
gate on 1d2db7b 0 uncommitted paths
bench_poll rc=0 :: 28/28 passed
bench_irq rc=0 :: 31/31 passed
lwip_poll rc=0 :: 17/17 passed
lwip_irq rc=0 :: 17/17 passed
web_poll rc=0 :: 8/8 passed
web_irq rc=0 :: 8/8 passed
DONE
```

The first line is the commit and the number of uncommitted paths. After `rc=`, the exit status
of the suite, comes its line with `passed`, or the last line of its log if it has none, which
says why it did not get there. For the web suites the status is 3 if the example did not compile,
4 if it did not upload, 5 if the board was not found, and otherwise that of `webtest.py`. `DONE`
is the last line, and is missing if the gate did not get to the end. The counts above are those
of release 1.2.0 on the bench of the author; they grow when tests are added.

**The MAC address of the web example.** The example does not print it, and the gate finds the
board by it: five seconds after an upload it pings the 254 addresses of the /24 of `--ip`, up to
12 times, and reads the neighbor table of the PC. The example starts the interface with
`begin()` and no address, so the core makes the MAC address from the unique ID of the board:
bytes 2 to 7 of the ID, the first one made unicast and locally administered, and 2 added to
the fourth (the number that lwIP gives the interface; core 6.3.0, `LwipIntfDev.h`). The ID is
the 16 hexadecimal digits in the name of the device in `/dev/serial/by-id` (set `port` to the
Pico wired to the ENC28J60):

```
port=$(ls /dev/serial/by-id/*Pico*)   # one Pico connected; otherwise name it
id=$(basename "$port" | grep -o '[0-9A-Fa-f]\{16\}' | tr A-F a-f)
printf '%02x:%s:%s:%02x:%s:%s\n' $(( (0x${id:4:2} & 0xFE) | 2 )) "${id:6:2}" "${id:8:2}" $(( (0x${id:10:2} + 2) & 255 )) "${id:12:2}" "${id:14:2}"
```

For the Pico of the bench of the author, `usb-Raspberry_Pi_Pico_E660C062131E3E27-if00`, it prints
`c2:62:13:20:3e:27`, the address that the author's own gate looked for. A way that does not depend
on the core: flash the example, ping the address that it prints on the serial port, and read
`ip neigh show <address>`; the MAC address follows `lladdr`.
